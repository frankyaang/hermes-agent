## 0. 核心问题回答

**家庭自主做饭双臂机器人的 MVP 不应定义为“像人一样完成所有厨房动作”，而应定义为：在受控家庭厨房场景中，让用户在不站灶、不持续看管的情况下，稳定吃上一顿安全、口味可接受、清理负担可控的高频热餐。**

建议 MVP 的一句话定义：

> **用户提供净菜/标准食材盒并完成少量前置准备，机器人在固定烹饪工位内自主完成 2–3 人份的一锅式或一菜一主食热餐，包括配料识别、下料、火候/温度控制、翻炒/搅拌、调味、出锅、安全停机和基础清洁；用户全程无需站在灶台前看管。**

这一定义刻意排除“全厨房自由移动、开冰箱、洗菜切菜、任意菜系、复杂摆盘、深度洗碗”等高难动作，因为这些能力虽然接近终局愿景，但不是验证用户是否愿意为“自主做饭”付费的最小闭环。MVP 的关键不是展示双臂机械能力，而是验证三件事：

1. **用户价值是否成立**：用户是否真的因为“不用站灶 + 热饭可吃 + 口味稳定”而持续使用。
2. **体验信任是否成立**：用户是否敢离开厨房，不需要一直盯着机器人。
3. **运营闭环是否成立**：菜谱、食材标准化、故障处理、清洁维护和售后能否低成本规模化。

## 1. MVP 边界定义

### 1.1 必须包含（MVP Must-have）

| 模块 | MVP 要求 | 用户价值 | 验证重点 |
|---|---|---|---|
| 固定烹饪工位 | 在固定灶台/电磁炉/一体化烹饪台上工作，不做全屋移动 | 降低安装和安全风险 | 家庭真实环境可部署 |
| 标准食材输入 | 用户放入净菜盒、预切食材或标准食材包 | 降低失败率，缩短准备时间 | 食材识别、重量/份量校验 |
| 3 类高频菜谱原型 | 一锅式盖饭/炒饭、快炒菜、汤面/炖煮类 | 覆盖“晚餐/简餐”高频需求 | 菜谱覆盖面与复购意愿 |
| 自主烹饪动作 | 下料、翻炒/搅拌、火候控制、调味、出锅 | 用户不用站灶 | 自主完成率、接管率 |
| 安全监控 | 防夹手、防碰撞、防高温/油溅、异常停机 | 用户敢离开厨房 | 安全零事故与告警可信度 |
| 基础清洁 | 锅铲归位、工位防溅、锅具/台面基础冲洗或提示清理 | 降低“做完还要收拾”的反感 | 清洁耗时和脏污残留 |
| APP/本机交互 | 选菜谱、确认食材、查看剩余时间、异常接管 | 降低学习成本 | 首次成功率、用户理解成本 |

### 1.2 可以延后（Should-have / V1.1）

| 能力 | 延后原因 | 进入下一阶段的触发条件 |
|---|---|---|
| 连续做两道以上复杂菜 | 多任务调度、锅具切换、保温和出餐顺序复杂 | 单餐自主完成率稳定 ≥85% 后扩展 |
| 个性化口味学习 | 需要足够复购数据 | D7/D30 留存证明高频使用后再做 |
| 更多菜系/任意菜谱 | 长尾菜谱会放大失败率 | 先验证 3 类烹饪机理，再扩展菜单库 |
| 食材订购/菜包生态 | 运营价值大，但会增加供应链复杂度 | MVP 用户明确愿为省事购买标准食材包 |
| 语音/多模态自然交互 | 体验加分但非核心闭环 | 基础交互足够稳定后再增强 |

### 1.3 明确不做（MVP Exclusions）

| 不做项 | 不做原因 |
|---|---|
| 打开冰箱并任意取菜 | 家庭冰箱布局非标、识别和抓取失败率高，且对“做饭价值”不是最小必要条件 |
| 洗菜、削皮、切复杂食材 | 食安和刀具风险高，动作种类复杂，容易拖垮 MVP 体验 |
| 任意厨房自由移动 | 安全、定位、家庭环境差异和保险责任过重 |
| 油炸、明火爆炒、整鱼整鸡等高风险菜 | 安全和清洁风险过高，不适合作为首批家庭验证场景 |
| 全自动洗碗/深度清洁 | 是完整家务闭环的一部分，但会把 MVP 从“做饭”扩成“厨房全流程机器人” |

## 2. 用户洞察排名表

| 排名 | 用户洞察 | 典型用户心声 | 对 MVP 的定义影响 | 运营判断 |
|---:|---|---|---|---|
| 1 | **用户买的不是“机器人会炒菜”，而是“我不用站在灶台前”** | “我下班累，只想有人把饭做出来。” | MVP 必须以“免看管”作为北极星，而不是以动作炫技作为北极星 | P0：无人值守完成率优先于菜谱数量 |
| 2 | **安全信任是家庭场景第一门槛** | “锅、火、刀、热油都在，机器人出错怎么办？” | MVP 要先限制工位、食材和菜谱边界，换取高安全确定性 | P0：安全红线未过，不进入家庭试点 |
| 3 | **口味稳定比菜系丰富更重要** | “会做 100 道但不好吃，不如 5 道稳定能吃。” | 菜谱数量不宜作为 MVP 成功指标，应先做少量高频菜谱稳定复现 | P0：3 类菜谱原型 > 50 道菜单宣传 |
| 4 | **用户不接受“省了做饭，增加了准备和清洁”** | “如果还要我洗切摆一堆盒子、做完刷半小时，就没意义。” | MVP 必须把用户主动操作时间纳入验收，而非只验机器人烹饪过程 | P0：用户主动时间 ≤5–8 分钟/餐 |
| 5 | **双臂不是卖点本身，双臂必须转化为体验优势** | “我不关心几只手，我关心它能不能真做饭。” | MVP 要验证双臂在控锅+翻炒、下料+搅拌、出锅+防洒中的必要性 | P1：形成“单臂/锅机做不到”的差异化证据 |
| 6 | **家庭厨房非标，越开放越难规模化** | “我家厨房很小/台面乱/锅不一样。” | MVP 应先走“半标准化工位 + 标准食材容器”路线 | P0：安装/适配成本必须可控 |
| 7 | **运营成功取决于菜谱、食材、售后和故障恢复** | “失败一次我可能就不用了。” | MVP 需要同时设计数据看板和客服 SOP，而不是只做硬件 Demo | P0：试点期间所有失败可归因、可复盘 |

## 3. 用户体验验证标准

### 3.1 北极星指标

**MVP 北极星指标：有效免看管成餐率。**

定义：用户完成食材放置和菜谱确认后，无需持续看管，机器人在限定时间内完成可食用热餐，且无安全事件、无重大清洁负担、用户愿意再次使用。

建议拆成以下 6 个一级指标：

| 指标 | 建议 MVP 门槛 | 说明 |
|---|---:|---|
| 自主完成率 | 家庭试点 ≥85%，实验室 ≥90% | 从开始烹饪到出锅无需人工接管 |
| 用户主动时间 | ≤5–8 分钟/餐 | 包含放食材、确认菜谱、餐后基础收尾 |
| 安全事故 | 0 起 | 包括夹碰、高温伤害、火/烟/油异常、食材飞溅失控 |
| 口味满意度 | ≥4.0/5 或 ≥75% 愿意复吃 | 以家庭成员评价为准，不只看操作者 |
| 清洁负担 | 餐后额外清理 ≤5 分钟 | 超过该门槛会抵消省事价值 |
| 7 日复用 | 试点家庭 D7 至少使用 3 次 | 验证不是一次性新鲜感 |

### 3.2 关键体验闸门

| 闸门 | 通过标准 | 未通过时的产品含义 |
|---|---|---|
| 安全闸门 | 连续家庭仿真测试无高危事件；异常可自动停机并可解释 | 不能进入真实家庭开放试点 |
| 免看管闸门 | 用户无需站在灶台前，异常只需按提示轻量处理 | 仍是“辅助厨具”，不是自主做饭机器人 |
| 可食用闸门 | 家庭成员认为“能作为一顿正餐”，不是“能吃但不会再吃” | 技术演示成立，但用户价值不成立 |
| 准备负担闸门 | 食材摆放/确认流程不比自己下锅更麻烦 | 标准化方案过重，需要重设食材输入 |
| 清洁闸门 | 做完后厨房状态可接受 | 用户会把负担从烹饪转移到清洁，影响留存 |
| 失败恢复闸门 | 失败原因可定位，用户知道下一步怎么做 | 售后成本和信任成本会失控 |

## 4. MVP 看板指标架构

| 看板层级 | 指标 | 目标用途 | 运营动作 |
|---|---|---|---|
| 战略层 | 有效免看管成餐率、D7/D30 复用、愿付费意愿 | 判断 MVP 是否成立 | 决定是否扩大试点/进入量产评审 |

## 6. 递归论证

### 6.1 为什么 MVP 不应做“全流程自动做饭”？

第一层原因是**家庭厨房非标**：冰箱位置、台面高度、锅具、食材包装、灶具、插座和动线都不同。机器人越开放，失败点越多。  
第二层原因是**用户价值并不等于动作完整性**：用户真正想买的是“热饭按时做好、我不用盯着”，不是“机器人必须从冰箱取菜再切菜”。  
第三层原因是**运营不可控**：全流程会带来食材识别、刀具安全、清洁、售后责任和保险问题，试点失败会迅速摧毁信任。

因此，MVP 应先用标准食材输入和固定工位换取高确定性，只验证“自主烹饪成餐”这条主价值链。

### 6.2 为什么“菜谱少但稳定”优先于“菜谱多”？

做饭机器人早期的用户信任非常脆弱。一次糊锅、夹手、洒汤、半生不熟，都会让用户从“愿意试”转为“不敢用”。因此，菜谱数量不是 MVP 的核心成功指标。更合理的顺序是：

1. 用少数菜谱覆盖关键烹饪机理；
2. 把每个菜谱的成功率、口味、清洁和接管率打稳；
3. 再复制到更多菜谱。

也就是说，MVP 要证明的是“这个系统可以可靠做饭”，而不是“菜单库看起来很大”。

### 6.3 为什么双臂能力必须被体验指标约束？

双臂机器人天然成本高、体积大、控制复杂。如果双臂只是在 Demo 中拟人化翻炒，而不能显著降低用户接管、提高出锅稳定性、减少溅洒或支持更复杂的真实菜谱，那么用户不会为“双臂”本身付费。MVP 需要专门设计“双臂必要性验证”：

- 一手稳定锅/盖/容器，另一手下料或翻炒；
- 一手控铲，另一手控调味/防溅；
- 一手出锅，另一手稳定餐盘；
- 与单臂、锅机、炒菜机方案做成功率和体验对比。

只有当双臂带来可量化的体验差异，双臂才是产品价值，而不是工程成本。

## 7. 推荐 MVP 版本定义

### MVP-0：内部工程样机（不进真实家庭）

- 场景：实验室家庭厨房模拟环境。
- 菜谱：3 个菜谱，覆盖一锅式、快炒、炖煮。
- 目标：验证机械动作、安全策略、菜谱执行链路。
- 通过标准：实验室自主完成率 ≥90%，无高危安全事件。

### MVP-1：封闭家庭试点（10–30 户）

- 场景：固定工位 + 标准食材盒 + 2–3 人份热餐。
- 菜谱：6–8 个高频菜谱。
- 目标：验证真实家庭是否愿意持续使用。
- 通过标准：家庭试点自主完成率 ≥85%，D7 使用 ≥3 次，口味满意 ≥4/5，用户主动时间 ≤8 分钟/餐。

### MVP-2：小规模商业试点

- 场景：限定城市/渠道，搭配安装、食材包和客服 SOP。
- 菜谱：10–15 个高频稳定菜谱。
- 目标：验证商业化和运营成本。
- 通过标准：D30 留存、售后工单率、安装成本、食材包复购、NPS 达到量产门槛。

## 8. 数据能力声明

本节点输入是一条产品策略问题，未提供真实 VOC 评论、用户访谈、竞品实测或质量反馈数据。因此，本报告属于**概念阶段的用户洞察与运营看板定义**，不是基于样本统计的定量结论。

建议下一步补充：

1. **目标用户访谈**：忙碌双职工、有娃家庭、老人家庭、单身/二人家庭，验证“自主做饭”的真实付费动机。
2. **厨房行为日志**：晚餐准备时间、站灶时间、清洁时间、外卖/预制菜替代场景。
3. **竞品/替代方案对比**：炒菜机、智能锅、预制菜、外卖、家政做饭服务。
4. **家庭试点实验**：用 Wizard-of-Oz 或半自动样机验证免看管、口味和清洁负担。
5. **安全和法规评估**：高温、燃气/电磁炉、儿童宠物、食品安全、责任边界。

## 9. 给父流程的结构化结论

- **MVP 核心定义**：固定工位 + 标准食材输入 + 3 类高频热餐 + 自主烹饪 + 安全停机 + 基础清洁。
- **最重要用户价值**：不站灶、不持续看管、稳定吃上热饭。
- **首要验证指标**：有效免看管成餐率，而不是菜谱数量或机械动作复杂度。
- **关键体验门槛**：安全 0 事故、家庭自主完成率 ≥85%、主动时间 ≤5–8 分钟/餐、口味满意 ≥4/5、餐后清洁 ≤5 分钟。
